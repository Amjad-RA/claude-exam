D1

Agentic Architecture and Orchestration

27%

1.1 The agentic loop: control flow driven by stop_reason

Send requestThe full history plus the tools
Read stop_reasonThe only field that controls the loop
"tool_use"Run the tools
Add to historyThe assistant turn, then a user turn with a tool_result for each tool_use_id
stop_reasonMeaningAction
tool_useClaude is calling a toolRun it, return the result, go round again
end_turnClaude finished naturallyUse the answer; the loop is done
max_tokensHit your max_tokensRaise the limit, or continue the response
pause_turnA server-tool loop hit its iteration limitSend the assistant content back to continue
refusalClaude declinedRead stop_details; retry on a fallback model
model_context_window_exceededThe response filled the context windowTreat it as truncated; trim or compact the context
Termination anti-patterns(1) Parsing the natural-language text for "done". (2) Using an iteration cap as the main stop. max_turns is a safety net, and hitting it is reported as error_max_turns, not success. (3) Treating any assistant text as completion. Also note: end_turn on the first response, with no tool call, is a valid finish.

Workflow vs agent

If code fixes the path, it's a workflow, even if it uses tool_use blocks. In an agent, the LLM directs its own process and chooses which tool to use next.

History hygiene

Send the assistant's full response, including its tool_use blocks, plus the tool_result blocks. Leave them out and Claude has no record of the result, so it may ask for the same call again.

1.2 Coordinator–subagent orchestration (hub and spoke)

  • All communication goes through the coordinator. Subagents never talk to each other, which gives you observability, error handling and controlled information flow.
  • Choose subagents per query. Don't run the full pipeline every time: parallelism cuts wall-clock time, but every call is still paid for.
  • Partition the scope completely. Facets that aren't assigned never show up in the report.
  • Refinement loop: synthesise, find the gaps, re-delegate targeted queries, and stop when coverage is enough.

1.3 Spawning subagents: Task tool and AgentDefinition

Context isolationA spawned subagent starts in a new, empty conversation. It sees its own system prompt and the coordinator's spawn prompt, never the coordinator's history, and only its final message comes back. Earlier decisions and findings must be written into the spawn prompt.
AgentDefinition fieldJob
descriptionWhen the coordinator should choose this subagent
promptThe subagent's standing system prompt: its role, expertise and constraints. The per-call prompt carries the specific task.
toolsAn explicit allowlist, e.g. ["Read","Grep"] for a read-only reviewer. Leaving it out gives the subagent every tool.
  • Parallel means several Task tool_use blocks in one coordinator response. One spawn per turn runs them one after another.
  • A delegation prompt states the goal and quality criteria rather than the steps, but still gives the objective, output format, tool and source guidance, and boundaries.
  • Pass on complete findings, keeping the content separate from source metadata.
  • Fork instead of spawning when the new branch needs the shared analysis so far.

1.4 Prerequisite gates and human handoff

PostToolUse on get_customerRecords "verified" only after a successful call
PreToolUse on process_refundDenies the call until that record exists
Claude plans the orderBut cannot skip the step
Exam trapsWriting the marker in PreToolUse on get_customer is wrong, because the marker exists even if the lookup fails. A system-prompt rule like "verify identity first" is guidance, not enforcement. A matcher like .*refund is an unanchored regex that also matches issue_refund_note; use ^process_refund$ or the plain exact name.

Multi-concern requests: run parallel investigations that share the case context, then combine them into one resolution. Handoff to a human: a structured summary they can act on without reading the transcript.

1.5 Agent SDK hooks

Matcher rules (tested against the tool name only)

  • *, an empty string or no matcher: all tools
  • Only letters, digits, _ - , | and spaces: exact name(s), e.g. Edit|Write
  • Any other character: an unanchored regex, e.g. mcp__billing__.* for every tool on one server
  • MCP tools are named mcp__<server>__<action>
  • Conditions on arguments go in the callback, reading tool_input

Decisions and normalisation

  • PreToolUse returns "deny" with a permissionDecisionReason that names the alternative (e.g. "call escalate_refund"), so the agent doesn't keep retrying
  • "ask" brings back a prompt; Claude never sees systemMessage
  • PostToolUse with updatedToolOutput replaces the output of any tool. updatedMCPToolOutput works only for MCP tools.
  • Use it to normalise mixed formats (Unix epochs, ISO dates, status codes) before Claude reads them
RuleAnything that must be guaranteed (refund limits, ordering, compliance) belongs in a hook. A prompt instruction always has some failure rate.

1.6 Task decomposition: fixed chain or adaptive?

Can you list the subtasks before the run?PatternExample
Yes, in a fixed orderPrompt chain sequenced in code, with gates between stepsSummarise, check in code, then translate into 3 languages
Yes, independent partsFixed parallel sectioningPer-file review passes, then a cross-file integration pass
No, they emerge as you goAdaptive: an orchestrator plans each next step from what it finds, with a stopping conditionInvestigating an incident from a vague alert
  • Writing "step 1, step 2" in a system prompt doesn't make a pipeline. Each step must be a separate call that your code sequences.
  • A bigger context window doesn't fix attention dilution in a 40-file review. Recall drops on every model.
  • Adding tests to a legacy codebase: map the structure, prioritise, then follow a plan that adapts as dependencies turn up.

A read-only "doc-reviewer" subagent must never edit files. The coordinator has Read, Edit, Write, Grep and Glob. What guarantees this?
  1. Write "never modify files" in its AgentDefinition prompt
  2. Leave tools unset so it inherits from the coordinator
  3. Set tools: ["Read","Grep"] on its AgentDefinition
  4. Set tool_choice to none
C. The tools field is an explicit allowlist. A prompt line is only guidance, and leaving tools unset grants every tool.
D2

Tool Design and MCP Integration

18%

2.1 Tool descriptions decide which tool is chosen

Claude matches the request against each tool's name and description, and nothing else about the tool. If two descriptions are near-identical, selection becomes a coin flip.

A description ready for selection covers

  • Purpose
  • Inputs, with examples
  • Edge cases
  • Boundaries against similar tools: when to use it and when not to

Fixing misrouting

  • Rename and rescope the overlapping tools; exclude the case the other tool handles
  • Split a generic tool into purpose-specific ones with clear contracts
  • Check the system prompt for keyword-triggered rules that pull calls away from the right tool
Exam trapChanging the order of tools in the array or adding backend priorities adds no signal. input_examples only supplement a description; they don't say when to use the tool.

2.2 Structured error responses for MCP tools

errorCategoryExampleisRetryableNext step

  • isRetryable asks: would the identical request succeed if sent again?
  • A generic "Operation failed" hides the category, so the agent can't choose a recovery.
  • A query with no matches is a success with an empty result. Don't set isError.
  • A subagent returns partial results plus a list of what failed and what it tried.

2.3 Scoping tools per agent and tool_choice

Selection gets less reliable as the tool count grows; compare 18 tools with 4–5. Give each role only the tools it needs (tools / disallowedTools), plus at most one narrow cross-role tool for a frequent need.

tool_choiceGuaranteeFits
{"type":"auto"}None: Claude decides (the default when tools are given)Agents choosing between acting and replying
{"type":"any"}Some tool is called, and Claude picks whichEvery turn must be a tool call
{"type":"tool","name":"x"}That specific tool is calledForcing a first step, e.g. extract_metadata
{"type":"none"}No tool callA text-only turn
Exam trapstool_choice controls whether a tool is called, not which tools exist. To stop out-of-role calls, remove those tools and keep auto. Forced any or tool errors with manual extended thinking, and Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1 return a 400. Models with adaptive thinking accept a forced call, but the response starts with the tool call and has no thinking block. Force the first call, then let later turns use auto.

  • On a name clash, local overrides project entirely. Nothing is merged and no error is raised.

  • Expose content catalogs as resources. Write tool descriptions that can compete with built-ins like Grep. Use an existing server before building your own.

D3

Claude Code Configuration and Workflows

20%

3.1 The CLAUDE.md hierarchy

Managed settings policy nobody can override, e.g. /etc/claude-code/
User: ~/.claude/CLAUDE.md only you, every project
Project: ./CLAUDE.md or ./.claude/CLAUDE.md the team, via git
Directory: api/CLAUDE.md loads on demand
  • At launch: the user file, plus project files at and above the working directory. On demand: subdirectory files, when Claude reads files there.
  • A teammate is missing a rule? It's probably in someone's user-level file, which never reaches the repo.
  • @path imports load whenever the importing file loads, so a root import is loaded at launch.
  • Split a monolithic CLAUDE.md into .claude/rules/ topic files. Use /memory to see which files actually loaded.
  • Organisation-wide policy belongs in managed settings, not a CLAUDE.md copied into every repo.

3.2 Slash commands and skills

Where they live

  • .claude/commands/x.md (project): shared once committed
  • ~/.claude/commands/: personal
  • .claude/skills/x/SKILL.md (project): shared
  • ~/.claude/skills/: personal, never in git
  • Precedence on a name clash: enterprise > personal > project

SKILL.md frontmatter

  • argument-hint: prompts the user for arguments
  • allowed-tools: pre-approves those tools. It doesn't remove others; use disallowed-tools for that.
  • context: fork: runs the skill in a subagent and returns only the result
  • disable-model-invocation: controls only who can trigger the skill
  • Only the description loads every session; the full content loads when it's used

Instructions Claude should always follow go in CLAUDE.md. A reusable procedure you invoke goes in a skill.

3.3 Path-scoped rules

---
paths:
  - "src/api/**/*.ts"
  - "src/**/*.{ts,tsx}"
---
  • paths is the only frontmatter field. Keys like include: don't work.
  • terraform/* matches only the top level; use terraform/**/* for nested files.
  • Patterns resolve from the repo root, so api/**/*.ts won't match src/api/.
  • For a convention scattered across many directories (e.g. **/*.test.tsx), use one path rule rather than a CLAUDE.md in every folder.

3.4 Plan mode or direct execution?

Plan mode

  • Many files, architectural reach, several valid approaches (a 45-file migration, splitting a monolith)
  • Claude reads and proposes; no edits until you approve
  • Then implement as direct execution
  • Use the Explore subagent to keep verbose discovery out of the main context

Direct execution

  • Clear scope and a known cause (a null check pinpointed by a stack trace)
  • Planning here only adds overhead
  • Risk of skipping a plan on big work: inconsistent patterns across files, then rework

3.5 Iterative refinement

  • When prose gets read in different ways, give 2–3 concrete input/output examples, including edge cases like nulls, empty cells and quoted commas.
  • Tests first: cover behaviour, edge cases and performance, then give Claude the actual failures.
  • In an unfamiliar domain, use the interview pattern: have Claude ask about design considerations before building.
  • Report failures whose fixes interact together in one message; fix independent failures one at a time.

D4

Prompt Engineering and Structured Output

20%

4.1 Explicit criteria reduce false positives

✓ Precise

  • Name the categories to report (bugs, security) and to skip (style, local patterns)
  • Wrap each category in its own XML tag: <security_criteria>
  • Give each severity level a concrete code example
  • Measure against the documented project standard (CLAUDE.md)
  • Switch off a noisy category while you rewrite it, to protect developer trust

✗ Vague

  • "Be conservative" or "only report high-confidence findings": no new rule, same mistakes, and real bugs get suppressed
  • Comparing against the most common style in the file, which may itself be legacy
  • Adjectives like "serious" for severity

4.2 Few-shot prompting

  • If the format still drifts despite detailed instructions, add examples in the exact target format.
  • Use 2–4 targeted examples that show why one action beat a plausible alternative. Twenty literal pairs teach matching, not judgment.
  • Contrast acceptable patterns with real issues.
  • Diversify length, language and structure. Regressions usually mean the examples share an accidental trait.
  • For extraction, include examples of vague or missing values handled honestly, otherwise the model learns to always invent a precise value.

4.3 Structured output with tool use

Extraction tool pattern

Define a tool you never run. Its input_schema is the output shape, and the tool_use.input is your result. To make sure it runs, force it with {"type":"tool","name":"extract_…"}. any lets Claude pick another tool. A forced call means no text before the call.

Schema design

  • Make fields the document may not contain optional or nullable. Required plus absent forces a made-up value.
  • Use closed enums with other and unclear as escape values
  • Put normalisation rules in the prompt
  • Strict mode guarantees structure (types, required fields, tool name), not semantics

4.4 Validation and retry with error feedback

ExtractWith strict schema validity
Validate in codee.g. calculated_total vs stated_total, conflict_detected
RetrySend the original document, the failed extraction and the specific errors
Or send to a personIf the value isn't in the source
  • A retry request carries nothing over from the first attempt, so it must include all three inputs.
  • If a field is still empty because the form was left blank, stop retrying. No model can recover a value that isn't there.
  • Add a detected_pattern field so dismissed findings can be analysed by code construct. A dismissal_reason field doesn't allow that.

4.5 The Message Batches API

The deal

50% cheaper, with no latency promise. Results arrive within a 24-hour expiry window. Use it for nightly or non-blocking work, never for a blocking merge gate.

Limits

At most 100,000 requests or 256 MB per batch, whichever comes first (a 413 if exceeded). custom_id: 1–64 characters of letters, digits, - and _.

Results

Not in submission order, so match them by custom_id. A batch can't be edited. Resubmit only the failed ids, with a fix, in a new batch. No client-side tool loops: each request is single-shot.

SLA formulainterval + 24 h ≤ SLA. A 48-hour SLA allows a nightly batch. A 30-hour SLA allows submitting every 4 hours (6 hours of slack, minus time to collect and process).

4.6 Independent and multi-pass review

  • The generating session is a weak reviewer: it reuses its own reasoning. More extended thinking or "critically re-examine" doesn't make it independent.
  • Independence means a fresh context: a second session or a new subagent. Resuming the generator's session isn't independent.
  • For big reviews, run per-file passes, then a cross-file integration pass, which settles conflicting per-file findings.
  • The finding pass aims for coverage and attaches confidence; a separate verification pass filters and routes the findings.
Line items sum to $940, but order_total reads $980. Both pass the strict schema. What is this, and what's the fix?
  1. A syntax error; tighten the schema
  2. A semantic error; add a check in code that recomputes the sum and compares it
  3. A model error; switch to a larger model
  4. Not an error, because the schema passed
B. Strict mode only guarantees types and fields. Relationships between fields have to be checked by your own validation code, and a failure can trigger a retry with error feedback.
D5

Context Management and Reliability

15%

5.1 Preserving critical facts in long conversations

The Messages API is stateless, so every turn resends the whole history. Context rot means recall drops as context grows, and a bigger window doesn't fix it.

Problems

  • Repeated summarisation blurs amounts, dates and customer expectations ($214.88 becomes "a refund soon")
  • Verbose tool payloads with 40+ fields pile up
  • Findings in the middle of long inputs get lost

Fixes

  • A persistent case-facts block kept outside the summary
  • Trim tool results in code to the relevant fields. Don't truncate or summarise them with a model.
  • Put a key-findings summary first and give each section a clear heading
  • Upstream agents return structured facts with metadata, not their reasoning

5.2 Escalation triggers

✓ Trigger 1

The customer explicitly asks for a human. Hand off immediately, without first trying a fix.

✓ Trigger 2

Policy is silent or ambiguous, e.g. a competitor price match when policy only covers your own site. Don't decline it and don't approve it.

✓ Trigger 3

The agent can't make meaningful progress.

Not triggersSentiment: for an angry customer with a solvable issue, acknowledge it, resolve it, and offer a human as an option. The agent's own sense of confidence or difficulty. If the customer repeats a preference for a person after your offer, then escalate. If a lookup returns several customers, ask for another identifier; don't pick "the most recent".

5.3 Error propagation across agents

Transient?A few local retries (rate limit, overload)
Can't clear?Report to the coordinator right away (e.g. an auth failure)
Structured payloadCategory, attempted action, partial results, alternatives
SynthesisAnnotate coverage: which findings are well supported, where the gaps are
Anti-patternsHiding an access failure as an empty success, so the report claims full coverage. A bare "search unavailable" or a status code like UNAVAILABLE. Halting the whole workflow because one source failed.

5.4 Context in large codebase exploration

  • Send verbose discovery (e.g. a 50,000-file search) to a subagent that returns only the final list. Compacting afterwards still floods the context first.
  • Use scratchpad files, one uniquely named file per concurrent subagent, and have the coordinator combine them. Read the notes back before answering.
  • /compact reclaims space but can drop details, so keep exact values in files. /clear starts clean.
  • Feed a summary of each phase into the next phase's subagent prompts.
  • For crash recovery, keep per-agent state exports and a coordinator manifest; skip the work that's already done.

5.5 Human review routing and confidence calibration

  • 97% overall can hide a failing segment. Break accuracy down by document type and field before reducing review.
  • Have the model give a confidence score per field on a defined scale, then calibrate it on a labeled validation set. A self-reported 0.9 isn't a measurement.
  • Route low-confidence or ambiguous items to people, e.g. weights with no clear unit (70% accurate). Let clean segments pass.
  • Keep taking stratified random samples of auto-accepted output to catch drift and new error patterns.

5.6 Provenance in multi-source synthesis

C S E D
  • Claim
  • Source (document or URL)
  • Excerpt that supports it
  • Date of publication or collection
  • A bibliography isn't provenance: each claim needs its own source.
  • When credible sources conflict ($420M vs $460M), report both with attribution and flag the conflict. Never average them.
  • With dates attached, different figures can show a trend rather than a contradiction.
  • Separate established from contested findings, and keep quotes word for word.
A customer asks for a human about a trivial issue. What does the agent do?

Hands off immediately. An explicit request is honoured without first trying a fix.

Where should exact refund amounts live in a long, summarised support chat?

In a structured case-facts block passed alongside every summary.

Concurrent subagents and scratchpads: one shared file or several?

One uniquely named file per subagent, combined by the coordinator after all of them finish.

How do you make a model's 0.9 confidence trustworthy?

Calibrate it against a labeled validation set, per field and per segment, and set thresholds where observed accuracy meets the target.
