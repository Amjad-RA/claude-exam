For mid- to senior-level solution architects, AI/ML engineers and tech leads. It tests solution design, model and context engineering, integration (MCP, RAG, auth, observability), evaluation, governance and safety, stakeholder and lifecycle management, and enabling teams on Claude Code.

D1

Solution Design and Architecture

17%

1.1 From business problem to Claude solution

Map the processToday's steps, and where the pain is
Choose Claude's stepsLLM or conventional code, step by step
Simplest shapeOne augmented call, then a workflow, then an agent
Build pathApps, Messages API, Agent SDK or Managed Agents
Tier per workloadSuccess criteria tied to business outcomes
Exam trapsSupport chat isn't one task. Split it into greeting, product information, conversation management and quotes, and evaluate each. "Touches several systems" doesn't mean you need an agent. Agent SDK means the loop runs in your process; Managed Agents means Anthropic hosts the loop, tools and runtime.

1.2 End-to-end architecture: input, processing, output, feedback

Who runs the tool?

  • Client tools (your code runs them): your own tools, plus Anthropic-schema tools like bash, text_editor and computer
  • Server tools (Anthropic runs them): web_search, web_fetch, code_execution, tool_search
  • pause_turn means the server loop hit its cap. Send the conversation back, including the paused response, to continue.

Feedback that corrects the run

  • Tool results feed the next turn
  • Hooks give deterministic behaviour, e.g. a PostToolUse hook on Edit and Write that appends to an audit log
  • Outcome loops use a separate grader in its own context; the agent doesn't grade itself
  • Use MCP for standard access to wikis, databases and chat tools

1.3 Augmented LLM, workflow or agent

Everything is built from the augmented LLM: a model with retrieval, tools and memory. The key question is who decides the next step: your code (a workflow) or the model (an agent). Agents trade latency and cost for flexibility.

PatternUse whenExample
Prompt chainingFixed steps, with programmatic gates between themWrite copy, translate it, then check the character limit in code
RoutingDistinct input categories, each with its own prompt or modelBilling, bug or cancellation tickets
Parallel: sectioningDifferent independent subtasks at onceA vulnerability check and a licensing check
Parallel: votingThe same task repeated to get diverse outputsSeveral runs judging one piece of code
Orchestrator-workersSubtasks only appear once the input arrivesMulti-file changes that can't be predicted
Evaluator-optimizerCriteria an LLM can critique, which improve with iterationLiterary translation. Use a code gate for hard rules like length.

1.4 Multi-agent design

  • Start with one agent. Split only for a concrete reason, mainly context isolation. A subagent's reads stay in its own context; only its final message comes back.
  • Multi-agent systems use 3–10× more tokens and are often slower overall. What they buy is thoroughness.
  • Divide work by context, not by role: the agent that writes a feature also writes its tests.
  • A self-contained brief has an objective, an output format, a tool list and boundaries. Leaving tools out gives the subagent every tool.
  • Invoke independent subagents in the same turn so they run concurrently.

1.5 Decomposition techniques

  • Chains are slower, since calls run in sequence; they buy accuracy. Parallel agents buy coverage, not savings.
  • Give each subtask its own model: Haiku for high-volume classification, Opus for complex remediation.
  • For a tight loop of many small tool calls, use programmatic tool calling, where code in the execution container calls the tools. Batches can't do this, because their requests are independent.
  • Use Agent SDK subagents with scoped tools and descriptions for audits that cover several dimensions.

1.6 Business value pillars

PillarMain lever and metric
EfficiencyCaching is the main item
TransformationA restructured workflow, or work that wasn't feasible before (e.g. paralegals move to reviewing exceptions)
ProductivityThe same workflow, more finished work per run
CostCost per completed task. Bank the free savings first.
Performance SLAsLatency and availability; meet them with the fastest, cheapest tier that's accurate enough
Exam trapBatch halves the cost but never fits an interactive SLA. Fast mode on a top tier fails the cost pillar for routine volume. Doing the same tasks faster is productivity, not transformation.

2.1 Choosing a model

ModelPositioned forLatency$/MTok (in / out)Default effort
Fable 5.1Demanding reasoning, long-horizon agentic workSlower$10 / $50high
Opus 5.5Long-running agentic coding and knowledge workModerate$4 / $20medium
Sonnet 5.5Best mix of speed and intelligenceFast$2 / $10high
Haiku 5.5High-volume classification, extraction, routingFastestFrom $0.10 / $0.50medium

All four: 1M-token context, 128K output, adaptive thinking (always on for Fable and Opus), text and image input. Haiku's price rises for prompts over 100K tokens. The Models API returns max_input_tokens, max_tokens and capability flags for each model.

  • Compare on cost per solved task, including failures and retries, not price per token.
  • If cost is too high, lower effort first (run an effort sweep on your evals); switch tier after that.
  • Fast mode is the same model with the same weights on faster inference, at a premium price.
  • Batches work on every active model at 50% off, so choose the model on quality.
  • Tier models inside one system so you spend frontier tokens only where they change the outcome.

2.2 System prompts and templates

Role its main job; one sentence already helps
Rules with reasons numbered steps where order matters
XML-tagged variable inputs the reusable template
Scenario responses and output format
Exam traps"NEVER use ellipses" in capitals is weaker than stating the reason. Prefill isn't supported on Claude 4.6 and later or Mythos Preview; define the format and show examples instead.

2.3 Few-shot and chain of thought

  • Go from zero-shot to one-shot to few-shot only when telling stops working. Use 3–5 diverse examples in <example> tags. Inconsistent labels or formatting are fixed by examples, not by asking for reasoning.
  • A uniform example set teaches its surface features. Diversify labels, edge cases and structure.
  • Chain of thought comes in three forms: basic ("think step by step"), guided (steps listed), and structured (<thinking> and <answer> tags).
  • Extended thinking blocks are at most a summary, and empty when display is omitted. For an auditable trail, use manual chain of thought in tags.
  • Long documents go at the top, above the query, instructions and examples.

2.4 Context window budgeting

One shared budget covers the system prompt, tool definitions, message history and tool results, the output, and thinking. Cached tokens still take up space in the window; caching only changes their price.

SituationAPI behaviour
The input alone exceeds the window400 error
Input plus max_tokens exceeds it (4.5+ models)Accepted; stops with model_context_window_exceeded if generation reaches the limit

Measure before a request with the token-counting endpoint and after with the usage fields. For tool-heavy agents, reduce cost with tool search, clearing tool results, and compaction.

2.5 Prompt reuse: caching, modular layout, Skills

Caching facts

  • Reuses a byte-identical prefix
  • Write costs 1.25× (5-minute TTL) or 2× (1-hour); reads cost about 0.1×
  • The TTL counts from the start of the request that wrote or read the entry, and refreshes free on each use
  • Up to 4 breakpoints, which are free; automatic caching is also available
  • Lookback is 20 blocks. Add a breakpoint further back if the gap grows past that.
  • Invalidation cascades tools → system → messages. A tool_choice change invalidates only the messages.

Layout and Skills

  • Order content from most stable to least; variables go last
  • SKILL.md name: lowercase letters, digits and hyphens; "claude" and "anthropic" are reserved
  • Progressive disclosure has 3 levels: the name and description always load, the body loads when used, linked files load on demand
  • A custom Skill uploaded in claude.ai belongs to that user; Skills uploaded through the API are shared workspace-wide
Do cached prompt tokens count toward the context window?

Yes. Caching changes their price, not whether they take up space.

Costs are too high. What's the first lever?

Lower the effort on the current model and sweep it on your evals. Change the tier after that.

A tool_choice change: what happens to the cache?

Only the messages cache is invalidated. The tools and system caches still hit.

Is a Skill named "claude-pdf-helper" valid?

No. "claude" and "anthropic" are reserved in the name field.

Integration

19%

3.1 Capability bloat

Overlapping, unused or vaguely described tools, and MCP servers the agent never calls, cost context and lower selection accuracy.

Source of the pressureRemedy
Overlapping or vague toolsMerge them into higher-level tools and namespace by service and resource. Tool search doesn't fix overlap.
Tools the role doesn't needScope them with tools, disallowedTools, mcpServers and permission modes
A huge catalog, each tool used rarelyTool search (deferred loading)
Repeated definitions cost moneyPrompt caching, which lowers the price but leaves them all in context
Old tool results piling upContext editing
Exam trapallowedTools only pre-approves tools; unlisted ones fall through to the permission mode and canUseTool. To lock the surface, combine it with permissionMode: "dontAsk", which denies everything else, or use disallowedTools. Subagents don't automatically get a subset of the parent's tools.

3.2 MCP authorization

  • The transport decides how a server authenticates: HTTP servers use OAuth, local stdio servers use environment credentials.
  • A server must reject tokens issued for other audiences and never pass a token on to downstream APIs; doing so creates a confused deputy.
  • 401 means not authenticated. 403 means the scope is insufficient: re-authorise with the union of the old scopes and the challenged scope (step-up). Logging in again the same way gives the same grant.

3.3 Accuracy vs latency

LeverClock it movesCost
A faster tierAll of themPossible loss of capability
Lower effortTotal time (fewer tokens)Less thoroughness. It doesn't reliably shorten the visible reply.
Fast modeOutput speedA premium price; same intelligence
StreamingPerceived responsiveness onlyTotal time is unchanged
Thinking display omittedText starts streaming soonerReasoning stays at full depth

Effort is soft guidance, and max is rarely worth it. Use low for simple subagent work. Justify a configuration with a sweep of effort and model, compared on cost per solved task and including re-runs of failures.

3.4 Observability at scale

  • Request logs can't explain a failed run. Use run-level telemetry: a parent span per turn with child spans for model calls, tools and subagents.
  • Roll out the OTel collector config through managed settings. Endpoints and credentials override the developer's, but exporter selectors follow per-key precedence, so pin them in managed settings too.
  • Tag with tenant, team and deployment. session.id and account attributes are on by default; turn off the ones you don't group by, to limit cardinality.
  • Turning on raw API body logging exposes everything the other content gates protect.

3.5 RAG ingestion

Contextual retrievalClaude writes a short, chunk-specific context that places each chunk within its document. Prepend it to the chunk for both the embedding and the BM25 index, and use prompt caching to keep this cheap. A generic document summary on every chunk doesn't give the same gain.
  • Chunk size, boundaries and overlap all matter. A chunk split off from its document loses context.
  • With Voyage embeddings, set input_type="document" for chunks and "query" for questions. Leaving it out loses quality.

3.6 Retrieval strategy

Data or query shapeStrategy
Corpus under about 200K tokens (~500 pages)Put it all in the prompt, with caching; no RAG needed
Exact identifiers and error codesBM25 (lexical)
Meaning and paraphrasesEmbeddings
Mixed trafficHybrid, with weights tuned to your data
An index would go staleJust-in-time retrieval by the agent, using tools
A long session near the context limitServer-side compaction

3.7 MCP, direct tools or agent-to-agent

MCP basics

  • 3 primitives: tools, resources, prompts
  • Transports: stdio (local) and Streamable HTTP
  • In Claude Code, an entry without a type is treated as stdio; a URL entry needs type: http, sse or ws
  • Messages API MCP connector: remote HTTPS servers only (Streamable HTTP or SSE), and tools only, not resources or prompts
  • Delegating to subagents is one level deep; use a wide fan-out

Which surface?

  • Claude Code CLI: interactive terminal work where you approve steps
  • Agent SDK: the loop and built-in tools (Read, Edit, Bash) in your process
  • Client SDK: you write the tool loop yourself (or use its beta tool runner)
  • Managed Agents: Anthropic hosts the loop, sandbox and event log

3.8 Progressive discovery: tool search

  • Selection accuracy drops with about 30–50 tools loaded. For example, 55K tokens of definitions from 5 MCP servers can be cut by over 85% with tool search.
  • Mark tools with defer_loading, but still send every full definition in the request; tool_reference blocks expand them as needed.
  • With fewer than about 10 small tools that are used constantly, load them all up front. Keep frequently used tools non-deferred.
  • Agent SDK ENABLE_TOOL_SEARCH=auto defers only once definitions reach 10% of the context window.
  • Built-in tool search is regex or BM25. For semantic matching, build a custom search tool that returns tool_reference blocks.
An agent combines 5 MCP servers, and their tool definitions use about 55K tokens before any work starts. It also keeps confusing two near-identical "search" tools. Which plan fixes both problems?
  1. Cache the tool definitions
  2. Turn on tool search only
  3. Merge and namespace the overlapping tools, then turn on tool search for the large catalog
  4. Switch to a larger model
C. Tool search removes definitions from context but doesn't separate tools that overlap. Merging and namespacing does. Caching only lowers the price.

Evaluation, Testing and Optimization

16%

4.1 Metrics

What to measureMetric
Fixed labelsExact match or F1 against labeled answers
Consistency across paraphrasesCosine similarity, which doesn't measure correctness
Summary vs a referenceROUGE-L (longest common subsequence, so overlap and order)
LatencyName the clock (TTFT, total time, end-to-end) and use a percentile, e.g. p95 under 200ms. Not a mean.
CostCost per completed task, with accuracy held fixed
Safety and securityA rate, given a named detector, sample size and ceiling, with a checkable definition of a successful attack

4.2 Eval datasets and graders

  • Make success criteria SMART first, e.g. "an average of at least 4/5 on a completeness rubric over 500 claims".
  • A test case has an input, an output, a golden answer and a score. Mirror real traffic, then deliberately add edge cases (malformed, scanned, non-standard inputs).
  • Volume beats hand-grading: many automated cases, repeated trials.
  • Choose the grader to fit: code (exact or string match), LLM (rubric), human. Keep human review to calibrate the LLM grader.

4.3 A/B testing and rollout

Baseline and targetSet before the change
Offline evalA held-out set, the same grader for both: the fast first check
Read by segmentAn aggregate can hide a regression
Live A/BDays or weeks, enough traffic; only for significant changes
Pinned versionsCanary, promote, roll back
Exam trapClaude's average confidence isn't accuracy. agents.update has no approval workflow, and callers using a bare ID get the newest version. Pin explicit versions in production.

4.5 Cost and latency: free wins first

Free wins (no quality cost)

  • Caching, which dominates agent-loop cost
  • Token hygiene and trimming inputs (measure context editing, which once cost more than it saved)
  • Batches for work that can wait: 50% off, up to 24 h, no streaming

Trade-offs (cost quality)

  • A smaller model
  • Lower effort
  • Tight caps

Bound spend with max_tokens (a cap, not a target), session and task budgets, and running at low effort then re-running failures.

1-hour cache: writes cost 2× instead of 1.25×. It pays only when about 1 in 20 gaps falls between 5 and 60 minutes. With requests 30–90 seconds apart, the 5-minute default is right.

4.6 OpenTelemetry

3 signals, all opt-in

Metrics (counters), log events (one record per event), traces (timed spans). CLAUDE_CODE_ENABLE_TELEMETRY=1 only enables collection. Each signal also needs its exporter (OTEL_METRICS_EXPORTER, OTEL_LOGS_EXPORTER, OTEL_TRACES_EXPORTER plus the beta flag), a protocol and an endpoint.

Cardinality

OTEL_METRICS_INCLUDE_SESSION_ID=false drops session.id and keeps model. The export interval affects only how often data is flushed, not cardinality.

Content gates

Content is redacted by default. OTEL_LOG_USER_PROMPTS also turns on responses unless OTEL_LOG_ASSISTANT_RESPONSES=0. Raw bodies expose everything.

Governance, Safety and Risk Management

14%

5.1 Guardrails chosen from the threat model

AdversaryThreatLayered controls
The userJailbreaks, direct injectionA Haiku pre-screen with a structured verdict (is_harmful), input validation, a hardened system prompt, throttling or bans for repeat offenders
A third party's contentIndirect prompt injectionUntrusted content only in tool_result blocks, JSON-encoded so it can't break out of its delimiters, plus an untrusted-content policy in the system prompt
No attackerHallucinationAllow uncertainty, ground claims in quotes, retract what isn't supported
  • If the screening model itself returns stop_reason: "refusal", treat that as a harmful verdict.
  • A classifier refusal is an HTTP 200 with stop_reason "refusal". Branch on stop_details.category; only display the explanation.
  • Haiku 5.5 has no server-side fallback, so build retries on the client.
  • Never put retrieved content in the system prompt: that gives it operator authority.

5.2 LLM failure modes

Hallucination

Clusters in precise specifics (deadlines, named sources). Tone doesn't track accuracy.

Knowledge

Frozen at the cutoff, with uneven coverage and inherited bias.

Context

Context rot sets in well before the hard limit, which is a separate cliff.

Interaction

Sycophancy, drift, over-reliance, partial steerability.

Prompt-level defences reduce but don't stop attacks, so red-team the system and design for breach: limit the blast radius and audit.

5.3 Human approval checkpoints

ModeBehaviour
default (Manual)Approves reads automatically; prompts for every edit, write and shell command
acceptEditsApplies file edits and common filesystem commands without asking
planRead-only exploration; file edits and shell writes go to canUseTool even if an allow rule matches
dontAskAnything not pre-approved is denied immediately and never reaches canUseTool (good for CI)
bypassPermissionsApproves only the calls that reach step 4; hooks and deny or ask rules still apply
Must rememberTo always require a person for wire transfers, even under bypass, use a PreToolUse hook that returns "ask". A tool listed in allowedTools never reaches canUseTool.

5.4 HIPAA, BAAs and ZDR

SurfaceWho processes the data
Claude API, Claude Platform on AWS, Microsoft FoundryAnthropic, so Anthropic's BAA and retention terms apply
Amazon Bedrock, Google Cloud Agent PlatformThe cloud provider
  • HIPAA readiness means a BAA plus a dedicated HIPAA-enabled organisation using only BAA-eligible features. The API rejects ineligible features. It's permanent and immediate.
  • Under ZDR, the API doesn't block ineligible features: the request goes through, and that data follows the feature's own retention.
  • HIPAA doesn't require ZDR. The BAA excludes the Console, and Enterprise plans aren't covered until the Primary Owner activates HIPAA.
  • To pilot a Covered Model inside a ZDR organisation, turn on 30-day retention in just that workspace.

5.5 Bias, fairness and honesty

  • Bias enters through training data, prompt examples, retrieval corpora and eval choices.
  • Measure fairness by comparing outcome metrics across groups and across phrasings.
  • If explanations vary with how a question is worded, standardise the decision factors they cite and re-test. A disclaimer doesn't fix it.
  • Claude aims to be calibrated (honest about uncertainty) and to respect epistemic autonomy (not steering the user to its own view).
  • Language, accessibility and channel are design choices that decide who gets excluded.
Wire transfers must always get human approval, even under bypassPermissions. How?

A PreToolUse hook on that tool that returns "ask". Hooks run first and hold in every mode.

An email body hides an injected instruction. Where should it go, and in what form?

Only in a tool_result block, JSON-encoded so it can't escape its delimiters, with an untrusted-content policy in the system prompt.

Under ZDR, does the API reject features that aren't eligible?

No. Only HIPAA readiness rejects them. Under ZDR the request goes through, and that data follows the feature's own retention.

D6

Stakeholder Communication and Lifecycle Management

14%

6.1 Discovery and requirements

  • The discovery brief covers users, needs, experience and constraints, plus the capability, speed and budget facts that drive the model choice.
  • A testable requirement is one an outsider can mark pass or fail. Use several criteria (quality, latency, cost, safety), each with a threshold.
  • Surface unknown requirements with a blind-spot pass, a prototype, interviews, references and a review of sample data.
  • Write acceptance tests before code. If all tests pass but the user is unhappy, the problem is upstream in the Description Chain.

6.2 Communicating trade-offs

A good recommendation includes

  • One recommended option, with its price in cost, speed, quality or risk
  • Evidence from your own eval; vendor numbers are only directional
  • Bounded residual risk: a limited write surface, a named worst case, audit coverage, spend limits. Never "zero risk".
  • The price of each extra layer of complexity, so the simpler design becomes the default

For engineers

  • Compaction summarises earlier turns automatically. Context editing clears old tool results or thinking blocks.
  • Claude 4.7 and later reject extended thinking with a budget (400); adaptive thinking is the only mode.
  • Use Managed Agents when nobody will run the infrastructure.

6.3 Expectations, SLAs and feedback

  • Limits are ceilings, not guarantees. Only Priority Tier has an uptime target: 99.5%, on committed capacity for a specific model version. Traffic over the commitment falls back to standard.
  • Rate limits and spend caps are maximums, and bursts can trigger 429s. The spend-cap 429 has no retry-after header and lasts until 00:00 UTC on the 1st of next month, unless you move up a tier.
  • Outages: check status.claude.com. Capacity-constraint messages are normal load management and not posted there.
  • Anthropic's retirement dates apply to the Claude API, Platform on AWS and Foundry. Bedrock and Google set their own.
  • Build the pilot feedback loop from day one, and tell a real quality drop from normal variation before reacting.

6.4 Architecture documentation

  • Pin down the components, data flows, models, tools and boundaries, and record why each layer exists.
  • Say where the loop runs: the Agent SDK runs in your process with local files, git and in-process tools; Managed Agents runs on Anthropic's infrastructure.
  • Document how tools connect, e.g. an existing Confluence or Jira MCP server launched locally over stdio.
  • To go from prototype to service, add configuration, error handling and deployment changes.
  • For cost and latency, recommend a smaller model. Raising effort adds thoroughness, not speed.

6.5 Lifecycle

DiscoverySuccess criteria and an eval set

Exam trapsRunbooks and caching don't belong in discovery. Once a capability eval passes almost everything, move it into the regression suite; don't drop it. After a model is retired, requests to it fail, so migrate within the deprecation window.

Developer Productivity and Operational Enablement

7%

7.1 Settings scopes and precedence

Managed settings organisation security policy
--settings JSON one session
.claude/settings.local.json personal, gitignored
.claude/settings.json team, code-reviewed
~/.claude/settings.json user
  • Single-value keys: the higher scope wins. Permission arrays: merged across scopes.
  • Rules are evaluated in the order deny, ask, allow, and specificity doesn't change that. A project deny Bash(aws *) still blocks a local allow Bash(aws s3 ls).
  • Team conventions go in the committed .claude/settings.json; managed settings are for security policy. Use CLAUDE.md for guidance and settings for enforcement.

7.2 Explore, plan, implement, commit

  • Keep reading and planning separate from editing. Use plan mode for exploring, then implement and commit.
  • Point Claude at exact files, sources and symptoms. @dir gives a file list; @file gives the contents.
  • Keep the session clean: interrupt, rewind, /clear, and send research to subagents.
  • Give Claude a check it can run: a test, a screenshot, a build.

7.3 Diagnosing configuration

CommandShows
/statusActive settings sources, including whether managed settings apply
/memory, /contextWhich memory files loaded, and what's in context
/hooksRegistered hooks. Matchers are case-sensitive, and a wrong one fails silently.
/mcpServer states: failed (see claude --debug=mcp), unapproved (approve it here), or connected with 0 tools (it started but returns no tool list)
/permissions, /doctorEffective rules; installation health

Being read isn't the same as winning: settings.local.json overrides settings.json. Isolate faults with safe mode or a clean config directory. If the problem persists, the cause is outside your user and project config.
