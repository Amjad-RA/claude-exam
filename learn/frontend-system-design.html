Networking

Every screen you build waits on the network. This module covers what happens between pressing Enter and seeing a page, then the three main ways a frontend talks to a backend: REST, GraphQL and gRPC.

2.1 How the web works

Typing https://example.com and pressing Enter starts a chain: find the server's address, open a connection, secure it, ask for the page, then turn the reply into pixels.

DNS: turning a name into an IP address

Browser and OS cachesAlready looked up recently? Use the cached IP until its TTL runs out.
Recursive resolverYour ISP's or a public one (like 1.1.1.1 or 8.8.8.8). It does the lookup for you.
Root serverDoesn't know the IP, but knows who runs .com.
TLD serverThe .com server points to example.com's authoritative name server.
Authoritative serverReturns the actual record (A for IPv4, AAAA for IPv6). Every layer caches it.

The layers a request travels through

HTTP application: methods, headers, status codes, body
TLS security: encryption and the server's certificate (the S in HTTPS)
TCP or UDP transport: TCP gives reliable, ordered delivery; HTTP/3 uses QUIC over UDP
IP network: routes packets to the server's IP address

From HTML to pixels

Parse HTML → DOMFinds CSS, JS and images and requests them, reusing the open connection.
Parse CSS → CSSOMCSS blocks rendering until it has loaded.
Render treeDOM plus CSSOM: only the nodes that are visible.
LayoutWorks out the size and position of every box.
Paint and compositeFills in pixels, then stacks the layers on screen.

HTTP versions

HTTP/1.1HTTP/2HTTP/3
Runs onTCPTCPQUIC over UDP
Requests per connectionOne at a time, so browsers open about 6 connections per hostMany at once (multiplexed streams)Many at once, and each stream is independent
FormatTextBinary frames, compressed headersBinary frames, compressed headers
Head-of-line blockingYes: a slow response holds up the queueGone at the HTTP level, but one lost TCP packet stalls every streamGone: a lost packet stalls only its own stream
HandshakeTCP, then TLSTCP, then TLSTransport and TLS 1.3 combined, so faster to connect
KeyA new origin costs a DNS lookup, a TCP handshake and a TLS handshake before the first byte arrives. That's why fewer origins, <link rel="preconnect"> and dns-prefetch hints, CDNs close to users, and connection reuse make pages faster.
Trap"DNS runs on every request." It doesn't: the answer is cached by the browser, the OS and the resolver until its TTL expires. Also, HTTPS hides the path, query, headers and body, but the domain usually still shows in the DNS lookup and the TLS handshake.

2.2 REST

REST (Representational State Transfer, from Roy Fielding's 2000 dissertation) is an architectural style, not a protocol. Everything is a resource with its own URL, and you act on it with standard HTTP methods. The server sends back a representation, usually JSON.

Constraints that make it REST

  • Client–server: UI and data storage evolve separately
  • Stateless: every request carries everything needed (for example the auth token); the server keeps no session between requests
  • Cacheable: responses say whether, and for how long, they can be cached
  • Uniform interface: resources named by URLs, changed through representations
  • Layered system: CDNs, proxies and load balancers can sit in between

Designing the URLs

  • Nouns, not verbs: GET /users/42, not /getUser?id=42
  • Plural collections, nested for ownership: /users/42/orders
  • Filter, sort and page with the query string: /orders?status=paid&page=2
  • Version the API: /v1/orders or a version header
  • The method says what happens; the URL says to what
MethodUsed toSafeIdempotent
GETRead a resource or a list✓✓
POSTCreate, or run an action✗✗
PUTReplace the whole resource✗✓
PATCHChange some fields✗Not guaranteed
DELETERemove a resource✗✓

Safe: doesn't change data on the server. Idempotent: sending it twice leaves the server in the same state as sending it once, so it's safe to retry.

StatusMeaningCommon ones
2xxSuccess200 OK · 201 Created · 204 No Content
3xxRedirect, or use your cache301 moved for good · 302 moved for now · 304 Not Modified

const res = await fetch("/api/v1/users/42", {
  headers: { Accept: "application/json" },
});
if (!res.ok) throw new Error(`HTTP ${res.status}`); // 404 and 500 don't reject
const user = await res.json();
Trapfetch only rejects when the request can't complete (network failure, CORS block, abort). A 404 or 500 resolves normally, so always check res.ok or res.status.

✓ Strengths

  • Simple, and works everywhere HTTP does
  • HTTP caching for free: GET responses cache by URL in the browser and CDN (Cache-Control, ETag → 304)
  • Easy to debug in the Network tab

✗ Weaknesses

  • Over-fetching: /users/42 returns 30 fields when the card shows 3
  • Under-fetching: a screen needs several calls (user, then orders, then items)
  • Changing a response shape needs a new version or a new endpoint

2.3 GraphQL

GraphQL is a query language for APIs, built at Facebook and open-sourced in 2015. The server publishes a typed schema; the client sends one query to a single endpoint (usually POST /graphql) naming exactly the fields it needs, nested as deep as the screen needs. The response has the same shape as the query.

# Schema (server)
type User  { id: ID!  name: String!  orders(last: Int): [Order!]! }
type Order { id: ID!  status: String!  total: Float! }
type Query { user(id: ID!): User }

# Query (client): one request for the whole widget
query {
  user(id: "42") {
    name
    orders(last: 3) { id status }
  }
}

# Response: same shape as the query
{ "data": { "user": { "name": "Asha",
    "orders": [{ "id": "7", "status": "SHIPPED" }, …] } } }

🔎 Query

Reads data. Like GET, but you choose the fields.

✏️ Mutation

Writes data, then returns the fields you ask for from the result.

📡 Subscription

Real-time updates pushed by the server, usually over WebSockets.

Schema (SDL)
The typed contract of every type and field. Clients can read it (introspection), which powers autocomplete and generated TypeScript types.
Resolver
A server function that fetches the data for one field. Nested fields call nested resolvers.
Fragment
A reusable set of fields. Each component can declare the fields it needs, and the page combines them into one query.
Normalized cache
Client libraries such as Apollo Client and Relay store objects by type and id, so updating one order updates every screen that shows it.
TrapGraphQL servers often answer HTTP 200 even when something failed: the problems are listed in an errors array, sometimes next to partial data. Checking res.ok alone misses them.

✓ Strengths

  • No over- or under-fetching: one round trip shaped like the screen
  • Strong types end to end, with tooling and codegen
  • New fields can be added without versioning; old ones are marked @deprecated
  • One API serves web, mobile and other clients with different needs

✗ Costs

  • HTTP caching is harder: one POST URL, so CDNs and the browser can't cache by URL (persisted queries over GET help)
  • N+1 queries on the server: a list resolver makes one database call per item, fixed by batching with DataLoader
  • Clients can send very expensive queries, so servers need depth and complexity limits
  • More setup than plain REST for a small API

2.4 gRPC

gRPC is a remote procedure call framework, open-sourced by Google in 2015. Instead of resources, you call methods on a service as if they were local functions. The contract is a .proto file; data travels as compact binary Protocol Buffers over HTTP/2.

syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);          // unary
  rpc WatchOrders (WatchRequest) returns (stream Order); // server streaming
}

message GetUserRequest { string id = 1; }
message User {
  string id   = 1;  // field numbers, not names, go over the wire:
  string name = 2;  // never reuse or renumber them
}
Call typeShapeExample
UnaryOne request, one responseGet a user
Server streamingOne request, a stream of responsesLive order status, a large export
Client streamingA stream of requests, one responseUploading sensor readings
BidirectionalBoth sides stream at onceChat, multiplayer state
BrowserCalls the backend with REST or GraphQL, as JSON.
BFF or API gatewayA backend-for-frontend shapes data for the UI.
Internal servicesTalk to each other with gRPC: fast, typed, streaming.
KeyBrowsers can't call a gRPC service directly: JavaScript can't control the HTTP/2 frames and trailers gRPC relies on. The browser uses gRPC-Web through a proxy such as Envoy, which supports unary and server-streaming calls only. That's why gRPC lives mostly between backend services.

✓ Strengths

  • Small and fast: binary payloads, multiplexed HTTP/2
  • Generated, typed clients in many languages from one .proto
  • Built-in streaming, deadlines and cancellation

✗ Costs

  • Not human-readable: you can't read it in the Network tab or test it with plain curl
  • Needs gRPC-Web and a proxy for browsers
  • No HTTP caching by URL

TipIn an interview, don't pick a winner; pick by the constraint. REST when caching and simplicity matter, GraphQL when screens need different shapes of related data, gRPC behind the BFF. Real systems often use all three.
What happens, in order, before the first byte of HTML arrives from a new site?

DNS lookup, TCP handshake, TLS handshake, then the HTTP request. Repeat visits skip steps thanks to DNS caching and connection reuse.

Why is HTTP/2 faster than HTTP/1.1 for a page with 80 assets?

It multiplexes many requests over one connection, instead of about 6 connections each handling one request at a time, and compresses headers.

PUT or PATCH to change just a user's email?

PATCH: it changes some fields. PUT replaces the whole resource, and is idempotent; PATCH isn't guaranteed to be.

401 or 403?

401: we don't know who you are (log in). 403: we know who you are, and you're not allowed.

What's the N+1 problem in GraphQL, and the usual fix?

Resolving a list of N items triggers one extra database call per item. Batch the calls with DataLoader.

Why don't browsers call gRPC services directly?

JavaScript can't control the HTTP/2 frames and trailers gRPC needs. Use gRPC-Web through a proxy such as Envoy (unary and server streaming only).

A dashboard widget shows a user's name and the status of their last three orders. With REST it calls /users/42, /users/42/orders, then /orders/:id three times, and users on slow mobile networks wait seconds. Other screens need different fields from the same data. What fixes this best?
  1. Move the calls to gRPC so the payloads are binary
  2. Use a GraphQL query that asks for exactly those fields in one request
  3. Set a longer Cache-Control max-age on each endpoint
  4. Paginate the orders endpoint
B. The cost is the number of round trips (under-fetching) plus unused fields (over-fetching). One GraphQL query returns the nested data in a single trip, and each screen picks its own fields. gRPC needs a proxy from the browser and doesn't reduce the trips; caching only helps repeat visits; pagination doesn't remove the extra calls.
This code shows "Hello, undefined" when the user doesn't exist, and the catch block never runs. Why?
try { const u = await (await fetch("/api/users/999")).json(); show(u.name); } catch { showError(); }
  1. The browser cached an old response
  2. await is missing before fetch
  3. fetch resolves on a 404; the code never checks res.ok
  4. The server should return 200 with an error message instead
C. fetch only rejects when the request can't complete. A 404 resolves with res.ok === false, and its JSON body has no name. Check res.ok and throw. Returning 200 for errors would make it worse.
The network drops while a request is in flight, and the client retries it automatically. Which request is safe to retry without risking a duplicate change?
  1. POST /orders
  2. POST /payments
  3. PATCH /cart with { "addItem": 7 }
  4. DELETE /orders/7
D. DELETE is idempotent: deleting order 7 twice leaves the same state as once. POST creates something new each time, and a PATCH that adds an item adds it again. To retry a POST safely, send an idempotency key the server can deduplicate on.

Networking at a glance

  • URL → DNS → TCP → TLS → HTTP → render
  • DNS answers are cached until their TTL
  • HTTP/2 multiplexes; HTTP/3 runs on QUIC over UDP
  • Fewer origins and preconnect save round trips
  • REST: nouns in URLs, the method is the verb
  • GET, PUT and DELETE are idempotent; POST isn't
  • 401 = who are you? 403 = not allowed
  • fetch doesn't reject on 404 or 500
  • GraphQL: one endpoint, exact fields, typed schema
  • GraphQL errors often arrive with HTTP 200
  • gRPC: .proto + protobuf + HTTP/2, four call types
  • Browsers need gRPC-Web and a proxy
